Case Study: Smart Healthcare Project Management and Monitoring System

A software development company has been contracted to develop a Smart Healthcare Project Management System for a network of five hospitals. The system must manage patient appointments, laboratory reports, doctor schedules, online consultations, and hospital billing. The project must be completed within 16 weeks, with a maximum approved budget of PKR 5,000,000.

The development team consists of a project manager, two backend developers, two frontend developers, one database developer, and one quality assurance engineer. During development, hospital management introduces additional requirements, including an AI-based preliminary diagnosis module and a mobile application. These changes increase the estimated project cost by PKR 800,000 and the development duration by three weeks. Furthermore, testing reveals critical defects in appointment scheduling and patient record management. The company requires a software-based solution to plan, execute, monitor, and control the project while managing scope changes, schedule delays, budget overruns, and quality issues.

Develop a complete, working Software Project Management System that allows the project manager to manage the healthcare software development project through an interactive graphical user interface and a database.

Generate a project schedule using activity start dates, end dates, and dependency relationships.

The backend calc.js executes a programmatic Critical Path Method (CPM) calculation:

  • Forward Pass: Computes Early Start ($ES$) and Early Finish ($EF$): $$ES_i = \max_{p \in Pred(i)}(EF_p), \quad EF_i = ES_i + Duration_i$$
  • Backward Pass: Computes Late Finish ($LF$) and Late Start ($LS$): $$LF_i = \min_{s \in Succ(i)}(LS_s), \quad LS_i = LF_i - Duration_i$$
  • Total Float (Slack): $Slack_i = LS_i - ES_i$. Activities with $Slack = 0$ constitute the Critical Path.
  • Identified Critical Path Activities: Requirements Analysis (A1) → System & Database Design (A2) → Database Implementation (A4) → Appointment Module (A5) → Billing Module (A7) → System Integration (A9) → Testing & QA (A10) → UAT (A11) → Handover (A12).

Identify delayed activities and calculate their impact on dependent tasks and deadline.

  • Case Study Delay: Activity A5 (Appointment & Scheduling Module) is delayed: at status date (2026-10-26), it is only 70% complete instead of 100%, causing a 7-day slip.
  • The engine automatically shifts downstream dependent tasks (Billing, Integration, Testing, UAT, Handover), pushing projected finish from 2026-12-21 to 2026-12-23 (2 days past deadline).

4. Cost Management and Earned Value Analysis (5 Marks)

Estimate activity costs and calculate the total planned project budget.

  • Each activity is assigned a bottom-up estimated planned cost. Total planned cost equals the Budget at Completion ($BAC = \text{PKR } 5,000,000$).
  • Actual expenditures ($AC$) are recorded per activity as invoices and developer hours are processed.

Implement Earned Value Management (EVM) Indicators:

EVM Indicator Formula Case Study Value Interpretation
Planned Value (PV) $\sum (BAC_i \times \% \text{Sched}_i)$ PKR 3,195,333 Value of work planned to be completed by Oct 26 status date.
Earned Value (EV) $\sum (BAC_i \times \% \text{Complete}_i)$ PKR 2,815,000 Budgeted value of work physically accomplished.
Actual Cost (AC) $\sum \text{Actual Cost}_i$ PKR 3,610,000 Actual money spent to date on activities.
Cost Performance Index (CPI) $EV / AC$ 0.78 Severe cost overrun: Project yields PKR 0.78 value per PKR 1.00 spent.
Schedule Performance Index (SPI) $EV / PV$ 0.88 Schedule slippage: Project progresses at 88% of planned schedule rate.
Cost Variance (CV) $EV - AC$ -PKR 795,000 Unfavorable cost variance.
Schedule Variance (SV) $EV - PV$ -PKR 380,333 Behind schedule.
Estimate at Completion (EAC) $BAC / CPI$ PKR 6,412,078 Forecasted total project cost exceeds budget by PKR 1,412,078.

Validate user inputs and maintain consistency between requirements, tasks, costs, change requests, and quality records.

  • Referential Integrity: Deleting an approved requirement is prohibited if it is linked to active WBS work packages or change requests.
  • Role-Based Assignment: Activities and defects cannot be assigned to arbitrary names; assignees must exist in the Project Charter's responsibility list.
  • Read-Only Decision State: Once a Change Request is decided (Approved/Rejected), its cost and schedule impacts are locked to prevent retroactive tampering.
  • Defect-Closure Enforcement: Marking a defect as In Progress or Resolved requires an assigned owner.
